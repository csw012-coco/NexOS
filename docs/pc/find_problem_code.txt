끔찍한 코드 판정 기준
1. 상태가 코드 밖에 숨어 있음

다음 중 하나면 위험 신호:

g_current_*, g_active_* 같은 전역 상태에 의존
함수 인자만 봐서는 어떤 장치·프로세스·컨트롤러를 건드리는지 모름
전역 구조체를 통째로 복사해서 “현재 객체”를 바꿈
함수 호출 순서에 따라 의미가 달라짐

예:

select_controller(1);
submit_request(req);

보다:

submit_request(controller, req);

가 훨씬 안전함.

판정
전역 상태 없이는 함수 의미를 알 수 없음: 끔찍함 +2
전역 상태가 실행 중 교체됨: 끔찍함 +3
2. 요청과 완료가 정확히 연결되지 않음

아래 같은 코드:

wait_for_next_event();

는 위험함.

안전한 형태는:

wait_for_event(request_id);
wait_for_trb(trb_phys);
wait_for_generation(generation);

즉 완료가 반드시 다음 중 하나와 매칭돼야 함.

요청 ID
TRB 주소
슬롯 + 엔드포인트 + 세대 번호
객체 포인터 + generation
명령 시퀀스 번호
판정
“다음 완료 이벤트”를 현재 요청 완료로 간주: +3
슬롯/엔드포인트만 보고 완료 처리: +2
타임아웃 후 늦은 완료를 구분 못 함: +3
3. 타임아웃이 단순 return 0으로 끝남

타임아웃 뒤에는 반드시 상태가 정의돼야 함.

요청은 아직 장치에서 실행 중인가?
링 위치는 어디인가?
버퍼를 재사용해도 되는가?
엔드포인트는 정상인가?
늦은 이벤트가 오면 어떻게 처리하는가?

이 질문에 답이 없으면 끔찍한 코드임.

나쁜 예:

if (!wait_done())
    return 0;

좋은 예:

if (!wait_done()) {
    req->state = REQ_TIMED_OUT;
    stop_endpoint(ep);
    cancel_request(req);
    reset_ring(ep);
    invalidate_generation(req);
    return -ETIMEDOUT;
}
판정
타임아웃 후 상태 복구 없음: +3
버퍼를 바로 재사용함: +3
늦은 완료 처리 규칙 없음: +2
4. 할당과 해제가 짝이 아님

찾아볼 패턴:

ptr = alloc();
if (!next_step())
    return 0;

중간 실패 시 이미 할당한 자원을 정리하지 않으면 누수임.

더 위험한 건:

DMA 버퍼
IRQ 등록
MMIO 매핑
디바이스 슬롯
VFS 등록
block device 등록
타이머 등록
판정
실패 경로에서 메모리 누수: +1
DMA/IRQ/MMIO 자원 누수: +2
해제된 객체를 하드웨어가 계속 참조 가능: +3
5. 등록 해제만 하고 실제 객체 종료는 안 함

예:

blockdev_unregister(dev);
dev->used = 0;

그런데 장치 쪽에서는 아직:

DMA 진행 중
endpoint running
IRQ 발생 가능
slot enabled
timer callback 예약됨

이면 use-after-free나 유령 이벤트가 생김.

정상 종료 순서:

새 요청 차단
→ 진행 중 요청 취소
→ IRQ/타이머 중지
→ 하드웨어 stop
→ 이벤트 drain
→ 등록 해제
→ 메모리 해제
판정
소프트웨어 플래그만 꺼서 종료 처리: +2
하드웨어가 계속 객체를 참조할 수 있음: +3
6. volatile을 락처럼 사용함

이런 건 락이 아님.

if (busy)
    return 0;

busy = 1;

두 CPU가 동시에 들어오면 둘 다 통과할 수 있음.

또 volatile은:

원자성 보장 안 함
메모리 순서 보장 안 함
락 보장 안 함
DMA 동기화 보장 안 함
판정
volatile int busy: +2
head/tail/count를 락 없이 여러 컨텍스트에서 수정: +3
IRQ와 일반 코드가 같은 구조체 접근: +3
7. 이벤트 큐 소비자가 여러 명임

특히 드라이버에서 위험함.

command_wait()도 event ring 읽음
transfer_wait()도 event ring 읽음
hotplug_poll()도 event ring 읽음

이러면 누가 먼저 읽느냐에 따라 남의 이벤트를 버림.

안전한 구조:

Event Ring 단일 소비자
→ event dispatch
→ command queue
→ transfer queue
→ port queue
판정
이벤트 원본 큐를 여러 함수가 직접 소비: +3
관련 없는 이벤트를 continue로 버림: +3
event type별 보관 큐 없음: +2
8. 실패를 무시하고 계속 진행함

위험한 패턴:

(void)reset_device();
(void)set_configuration();
(void)clear_halt();
continue_init();

의도적으로 무시할 수는 있지만, 그 경우에도:

무시 가능한 이유
실패해도 유지되는 불변식
이후 fallback

이 있어야 함.

판정
반환값을 무시하고 다음 단계 진행: +2
실패 후 구조체가 반쯤 초기화된 채 사용됨: +3
로그만 찍고 정상 상태로 취급: +2
9. 상태 전이가 문서화되지 않음

객체가 다음 상태를 가진다면:

NEW
INITIALIZING
READY
RUNNING
STOPPING
DEAD
ERROR

각 함수가 어느 상태에서 호출 가능한지 명확해야 함.

나쁜 코드:

if (dev->used)
    ...

used 하나로:

할당됨
초기화 완료
연결됨
사용 가능
제거 중

을 모두 표현하면 언젠가 꼬임.

판정
boolean 하나로 여러 상태 표현: +2
잘못된 상태 호출을 검사하지 않음: +2
실패 후 상태가 무엇인지 불명확: +3
10. 구조체 수명이 불명확함

포인터를 저장하는데 누가 소유하는지 모르면 위험함.

질문:

누가 생성하는가?
누가 참조를 보유하는가?
언제 해제 가능한가?
callback이 끝나기 전에 사라질 수 있는가?
자식 객체가 부모보다 오래 살 수 있는가?
판정
참조 카운트 없이 여러 곳에 포인터 저장: +2
detach 중 자식/콜백이 부모를 참조 가능: +3
raw pointer를 장기 큐에 저장: +2
11. 배열 인덱스와 하드웨어 값을 그대로 신뢰함

특히 위험:

array[slot_id]
array[port]
array[endpoint]

검증 없이 하드웨어 값이나 descriptor 값을 인덱스로 사용하면 안 됨.

판정
하드웨어 값을 배열 인덱스로 직접 사용: +2
상한 검사는 있는데 하한·예약값 검사 없음: +1
shift 크기가 외부 값에 의해 결정됨: +2
12. 매직 숫자가 상태 규칙을 숨김

예:

control |= 1u << 5;
control |= 1u << 16;

이 자체가 무조건 끔찍한 건 아니지만, xHCI 같은 복잡한 드라이버에서는 의미가 숨으면 검증이 어려움.

좋은 형태:

control |= XHCI_TRB_IOC;
control |= XHCI_TRB_DIR_IN;
판정
하드웨어 비트를 매직 숫자로 반복 사용: +1
같은 비트가 위치마다 다른 의미로 쓰임: +2
즉시 CRITICAL 판정 조건

아래는 점수 계산 없이 바로 치명적 판정해도 됨.

사용자 포인터 직접 역참조
DMA 대상 메모리를 완료 전에 재사용
해제된 메모리를 장치가 계속 참조 가능
lock 없이 같은 링을 여러 실행 흐름이 수정
타임아웃 난 요청과 다음 요청을 구분 못 함
이벤트를 잘못된 요청의 완료로 처리 가능
하드웨어 입력으로 커널 배열 범위를 넘길 수 있음
IRQ handler와 일반 코드가 동일 큐를 동기화 없이 수정
reference count가 0인데 객체 사용 가능
실패한 초기화 객체를 정상 객체 목록에 등록
점수표

각 함수나 서브시스템에 점수를 붙이면 꽤 쓸 만함.

0~2점    평범한 코드
3~5점    불안한 코드
6~9점    위험한 코드
10~14점  끔찍한 코드
15점 이상 폭발물

단, CRITICAL 조건 하나라도 있으면 점수와 상관없이:

CRITICAL

로 분류.

리뷰용 체크리스트

함수 하나를 볼 때 이것만 물어보면 됨.

1. 이 함수가 사용하는 상태는 인자로 드러나는가?
2. 동시에 호출될 수 있는가?
3. 요청과 완료가 정확히 매칭되는가?
4. 타임아웃 뒤 상태는 무엇인가?
5. 중간 실패 시 앞에서 만든 자원을 정리하는가?
6. 객체가 사라지는 동안 콜백·IRQ·DMA가 접근할 수 있는가?
7. 입력값과 배열 인덱스는 검증되는가?
8. 다른 함수가 같은 이벤트 큐를 소비하는가?
9. 실패 반환값을 호출자가 실제로 처리하는가?
10. 디버그 assert로 불변식을 검사하는가?

이 중 3개 이상 답이 불명확하면 위험, 5개 이상이면 끔찍한 코드 후보로 보면 됨.

가장 짧은 정의

NexOS에서 사용할 공식 정의를 한 줄로 줄이면:

끔찍한 코드란 정상 경로는 동작하지만, 실패·동시성·수명·복구 중 하나 이상이 정의되지 않아 실행 결과가 타이밍에 따라 달라지는 코드다.

그리고 더 짧게 줄이면:

실패했을 때 무슨 상태인지 모르는 코드.

더더 짧게 줄이면:

끔찍한 코드.

이 기준이면 단순히 스타일이 나쁜 코드와 실제로 커널을 터뜨리는 코드를 꽤 잘 구분할 수 있음.
